Overview

What Is Detectree2?

Detectree2 is an open-source Python package for automatic tree crown delineation in aerial RGB and multispectral imagery, built on the Detectron2 implementation of Mask R-CNN. It was developed by James Ball and colleagues in the Forest Ecology and Conservation Group (led by Prof. David Coomes) at the University of Cambridge's Conservation Research Institute.

  • Why it exists: lidar-based canopy segmentation struggles to isolate individual trees where crowns overlap densely — common in tropical forests
  • Its approach: treat crown delineation as an image instance-segmentation problem, not a lidar point-cloud problem
  • License: MIT, distributed via PyPI (pip install detectree2)
  • Citation: Ball et al. (2023), Remote Sensing in Ecology and Conservation, 9(5):641-655

Core Function

What It Actually Does

Given an orthomosaic, detectree2 outputs a polygon outline for every individual tree crown it finds — not just a bounding box. Each polygon carries a confidence score, and because it's instance segmentation, it can tell two touching or overlapping crowns apart as separate trees.

  • Input: a georeferenced RGB (or multispectral) orthomosaic — a GeoTIFF
  • Output: crown polygons (GeoJSON/shapefile), each with a confidence score, ready to overlay in QGIS
  • Unit of detection: one polygon = one tree, shape included — not just "tree present here"
  • Extendable: designed for single-class (tree) delineation, but can be trained multi-class — opening the door to low-cost species mapping

Detection vs. Delineation

A plain object detector would draw a box around each tree. Detectree2 draws the actual crown shape — critical for canopy-area measurement, not just counting.

Why Mask R-CNN

Mask R-CNN extends a standard detector with a per-instance segmentation mask branch — exactly the "shape, not just box" capability crown delineation needs.

Applications

Where It's Used

Originally built for tropical forest monitoring, detectree2 is now used across a range of ecological and conservation applications, and has been independently validated well beyond its original tropical setting.

  • Tropical forest monitoring: tracking individual tree growth and mortality over time
  • Conservation research: canopy structure and biodiversity mapping
  • Carbon / ecological studies: crown-area-based biomass estimation
  • Beyond the tropics: independently validated on a temperate deciduous forest in Japan, outperforming DeepForest (Gan et al. 2023)

In This Project

Detectree2 is Step 0 of our Tree-Crown Species Pipeline — it finds and outlines every crown in a drone orthomosaic. Everything after that (species clustering) is our own code, layered on top of its output.

drone orthomosaic → Detectree2 detects crowns → DINOv2 embeds each crown → KMeans clusters by visual similarity → human labels species
Methodology

The Standard Detectree2 Workflow

Per detectree2's own documentation, the intended end-to-end workflow has four stages — training a model is part of the standard process, not optional:

  1. Tile the orthomosaic and reference crown data, for training/validation/testing
  2. Train (and tune) a Mask R-CNN model on the training tiles
  3. Evaluate performance on held-out test tiles against manually-drawn crowns
  4. Predict crowns over the full region of interest with the trained model
Our project only runs step 4. We use detectree2's pre-trained weights (from its model_garden, plus our own fine-tuned .pth files) and go straight to prediction — no training or evaluation happens inside this codebase.

Why that's fine

Pre-trained models already generalise reasonably well to new areas; detectree2's own docs note it can be fine-tuned to a new region with as few as ~10 manually-annotated images if needed.

Our Implementation

How It Runs in predict.py

Every step below runs inside run_detectree2_pipeline() — tagged by whether the step is detectree2's own code, or ours layered around it.

  • CUSTOM Downsample the ortho to a consistent effective resolution (GSD-adaptive, this week's fix)
  • DETECTREE2 Tile the ortho into overlapping tiles — tile_data()
  • DETECTREE2 Load weights into a Mask R-CNN predictor — setup_cfg() + DefaultPredictor
  • DETECTREE2 Run inference per tile — predict_on_data()
  • DETECTREE2 Convert pixel-space masks to geo-referenced polygons — project_to_geojson()
  • DETECTREE2 Stitch crowns back together across tile boundaries — stitch_crowns()
  • DETECTREE2 Clean duplicates via IoU + confidence filtering — clean_crowns()
  • CUSTOM Filter by crown area (4-200 m²) and simplify polygon vertices (0.6m tolerance)

Frontend Parameters

In Our UI: Detectree2 vs. Not

The Step-3 parameter form is grouped by pipeline stage — only the first group is actually detectree2.

Detectree2 — "Detection" group
  • modelKey Detector model dropdown — which crown-detection weights to use
  • p_tile tile_size (m) — default 10
  • p_buf buffer (m) — default 10
  • p_iou iou_threshold — default 0.9
  • p_conf conf_threshold — default 0.85
NOT Detectree2 — later stages
  • backbone DINOv2 feature extractor — "Crown embedding" group, a separate model entirely
  • p_pca pca_components — "Clustering" group (default 50)
  • klist k_list — candidate K-Means cluster counts (default 2,4,6,8,10)
  • p_epsg CRS fallback — georeferencing utility, not a model parameter at all
Deliberately hidden from the UI entirely: batch_size (VRAM-bound, fixed at 64) and img_size (fixed by whichever DINOv2 backbone is chosen — sent automatically, never a free field). Neither is a detectree2 parameter either — both belong to the DINOv2 embedding step.
Summary

Key Takeaways

  • Detectree2 is a crown-finding engine, nothing more. It answers "where are the trees and what shape are their crowns" — that's its entire job.
  • It's Mask R-CNN under the hood (via Detectron2), from Cambridge's Forest Ecology and Conservation Group, peer-reviewed and independently validated beyond its original tropical setting.
  • Our pipeline only uses its "predict" stage — pre-trained weights, no training/evaluation happening in this codebase.
  • Species identification is entirely ours, not detectree2's. DINOv2 feature embedding, PCA, and K-Means clustering are separate stages we built on top of detectree2's crown output.
  • In the frontend, only 5 fields are truly detectree2 — model choice, tile_size, buffer, iou_threshold, conf_threshold. Everything else in the parameter form belongs to a later, unrelated stage.
This distinction matters for debugging: if crown detection looks wrong, the fix is in detectree2's parameters or weights. If species clustering looks wrong, detectree2 isn't the place to look — that's DINOv2/PCA/K-Means territory.
